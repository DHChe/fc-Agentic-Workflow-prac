## 지금 막힘 (blocker)
### 1. 영수증 분석 결과 규칙과 실제 시험이 서로 다르다 (리뷰어 2명 모두 지적) [원문: S1 / §6.2]
- 무슨 문제: 영수증 분석 결과가 어떤 형태로 나와야 하는지 정해둔 `JSON Schema`(=데이터 설계도)와, 값이 없을 때 무엇으로 대체할지 정하는 `nullable()`(=값 없어도 허용)·`catch()`(=대체 값 지정) 기능, 그리고 실제로 시험하는 `Vitest`(=프로그램 시험 도구)의 기대값이 서로 맞지 않습니다. 특히 이 값이 "반드시 있어야 하는(`required`)" 것인지에 대한 부분이 혼란스럽습니다.
- 왜 중요한지 (비유): 레시피에 "설탕은 반드시 넣으세요"라고 적혀 있는데, 요리사는 "설탕 없으면 꿀로 대체할게요"라고 말하고, 맛 평가자는 "설탕은 중요하지 않아요"라고 평가하는 것과 같습니다. 이렇게 제각각이면 어떤 맛이 나올지 알 수 없습니다.
- 그냥 두면: 영수증 분석 결과가 규칙대로 나오지 않아, 앱이 올바르게 처리하지 못하고 오작동할 수 있습니다.
- 선택지와 추천:
    *   현재의 `Zod`(=데이터 검증 도구) 규칙에 따라 어떤 값이 반드시 있어야 하는지(`required`) 정확히 확인하고, 시험 결과도 그에 맞게 바꿉니다.
    *   모델에게 선택권을 주려면 `catch()` 대신 `optional()`(=선택적)이나 `default()`(=기본값)를 사용하고, 반드시 있어야 할 값들을 표로 정리합니다.
    *   (추천) 현재 `catch()` 방식을 유지하되, `plan.md`(=계획서)와 `step1.md`(=구현 단계 파일)의 기대값을 실제 데이터 변환 규칙에 맞게 고칩니다. 누락된 값을 복구하는 정책과 AI에게 요청할 필수 값 목록을 명확히 구분하여 설명합니다.
- 당신이 답할 질문: 영수증 분석 결과의 필수 항목 규칙을 현재 `Zod` 동작에 맞출까요, 아니면 선택 기능을 다르게 쓸까요?

### 2. 시험 도구 `Vitest` 버전이 고정되지 않아 오류가 난다 [원문: S0]
- 무슨 문제: `Vitest`(=프로그램 시험 도구)를 설치할 때 특정 버전을 지정하지 않아, 최신 버전(Vitest 5)이 설치됩니다. 하지만 이 최신 버전은 `Node`(=웹 프로그램 실행 환경)의 특정 버전(22.12 미만)에서는 작동하지 않아, 프로그램 시험이 실패합니다.
- 왜 중요한지 (비유): 새 집을 짓는데 최신 공구를 가져왔더니, 우리 현장의 전압이 낮아서 공구가 작동하지 않는 상황과 같습니다. 작업이 시작부터 멈춰버립니다.
- 그냥 두면: 앱 개발 초기 단계부터 시험이 계속 실패하여, 다음 단계를 진행할 수 없습니다.
- 선택지와 추천:
    *   `step0.md`(=구현 단계 파일)에서 현재 `Node` 버전이 22.12 미만이면 작업을 중단하고, 최신 `Node` 사용을 권장합니다.
    *   (추천) `step0.md`에서 `vitest@4`(=Vitest 4버전)를 사용하도록 버전을 고정하여, 현재 앱 환경(`Next 16`의 최소 `Node` 버전)과 충돌하지 않게 합니다. `package.json`(=프로젝트 도구 목록)에 `Node` 버전 제한을 명시합니다.
- 당신이 답할 질문: `Vitest` 버전을 이전 버전으로 고정하여 `Node` 버전 문제를 해결할까요?

### 3. Claude AI 호출 설정이 AI 모델의 기본 작동 방식과 충돌한다 [원문: S4 / ADR-005 / §5.6]
- 무슨 문제: `Claude Sonnet 5`(=AI 모델 이름)는 기본적으로 `adaptive thinking`(=스스로 생각하는 방식)과 `effort high`(=최선을 다해 노력)로 작동하는데, AI의 `max_tokens`(=최대 글자 수)와 `timeout`(=최대 대기 시간) 설정이 너무 짧게 되어 있어 충돌이 일어납니다. AI가 충분히 생각하거나 답변할 시간을 주지 않는 설정입니다.
- 왜 중요한지 (비유): 똑똑한 비서에게 "충분히 고민해서 보고서를 써줘"라고 지시했는데, "보고서는 100자 이내로, 1분 안에 끝내"라고 명령하는 것과 같습니다. 비서가 제 능력을 발휘할 수 없습니다.
- 그냥 두면: AI가 영수증 분석을 제대로 수행하지 못하고, 시간이 초과되거나 오류를 내면서 작업이 중간에 멈출 것입니다.
- 선택지와 추천:
    *   (추천) `max_tokens`를 16384 이상으로 늘리고, `thinking: { type: 'disabled' }`(=생각 기능 끔) 또는 `output_config: { effort: 'low' }`(=노력 수준 낮음) 설정을 사용하여 AI의 작업 방식을 조정합니다.
    *   `timeout`을 AI의 생각 시간을 고려해 충분히 늘리거나, 생각 기능을 끈다면 45초로 유지합니다.
- 당신이 답할 질문: AI 호출 설정을 AI 모델의 기본 작동 방식에 맞춰 조정할까요?

### 4. 품목명·가맹점 이름을 `null`(=값이 없음)로 처리하려는 규칙과 `string`(=글자) 타입 선언이 충돌한다 [원문: S1]
- 무슨 문제: 영수증 품목명(`LineItem.name`)과 거래 가맹점(`Transaction.merchant`)을 `string`(=글자) 타입으로 쓰겠다고 선언했지만, 200자를 초과하면 `null`(=값이 없음)로 보정하려는 규칙이 있습니다. 글자로 정했는데 값이 없게 만들면 서로 모순됩니다.
- 왜 중요한지 (비유): "여기는 반드시 글자를 써야 하는 칸입니다"라고 말해 놓고, 글자 수가 많으면 "아무것도 쓰지 마세요"라고 지시하는 것과 같습니다. 혼란스럽고 시스템이 오작동할 수 있습니다.
- 그냥 두면: 데이터 타입 불일치로 인해 앱이 데이터를 처리하는 과정에서 오류가 발생하거나, 예상치 못한 동작을 할 수 있습니다.
- 선택지와 추천:
    *   최상위 가맹점 이름(`merchant`)이 `null`을 허용하는 것과, 품목명/가맹점 이름(`name`/`merchant`)이 항상 글자(문자열)를 유지하는 것을 구분합니다.
    *   (추천) 중첩된 필드(예: 품목명, 가맹점명)는 `z.string().max(200).catch('')`(=글자 수를 200자로 제한하고, 값이 없으면 빈 글자로 대체)와 같이 항상 글자 값을 가지도록 통일하고, `step1.md`(=구현 단계 파일) 검증 과정에 이를 포함합니다.
- 당신이 답할 질문: 품목명·가맹점 이름을 항상 글자 값으로 유지하는 방향으로 규칙을 통일할까요?

- 그냥 두면: 사용자가 알 수 없는 영수증을 수정할 수 없어, 앱의 유용성이 크게 떨어집니다.

- 당신이 답할 질문: 알 수 없는 영수증일 때 안내 화면과 수정 입력창이 동시에 보이도록 할까요?

### 6. 영수증 사진 한 장에 여러 장의 영수증이 있을 때 처리 규칙이 문서마다 다르다 (리뷰어 2명 모두 지적) [원문: §7.3 / S4 / USER_FLOWS 11절]
- 무슨 문제: `USER_FLOWS.md`(=사용자 흐름 문서)에서는 "첫 번째만 인식"한다고 하고, `step4.md`(=구현 단계 파일)와 `plan.md`(=계획서)에서는 "가장 크게 보이는 한 장만", 그리고 `plan.md` §7.3에서는 단순히 "한 장만 인식"한다고 되어 있습니다. 어떤 규칙을 따라야 할지 혼란스럽습니다.
- 왜 중요한지 (비유): 물건을 살 때 어떤 매장에서는 "선착순 할인", 다른 매장에서는 "가장 비싼 상품 할인"이라고 제각각 말하는 것과 같습니다. 기준이 없으면 소비자는 혼란스럽습니다.
- 그냥 두면: AI가 어떤 영수증을 분석해야 할지 헷갈려 하여, 잘못된 영수증을 분석하거나 아예 분석을 실패할 수 있습니다.
- 선택지와 추천:
    *   (추천) 모든 문서를 "가장 크게 보이는 한 장"으로 통일하거나, "첫 번째만 인식"으로 맞춥니다.
- 당신이 답할 질문: 영수증 사진 한 장에 여러 영수증이 있을 때 "가장 크게 보이는 한 장"만 인식하도록 규칙을 통일할까요?

### 7. 상세 페이지에서 사용자 정보를 가져오는 명령이 빠져 있다 [원문: S6]
- 무슨 문제: 영수증 상세 페이지(`[id]/page.tsx`=영수증 상세 화면 파일)에서 사용자 ID(`user.id`)를 사용하지만, 이 사용자 정보를 가져오는 `getCurrentUser()`(=현재 사용자 정보를 가져오는 함수) 호출 지시가 빠져 있습니다.
- 왜 중요한지 (비유): 어떤 사람이 들어와야 문을 열어줄지(사용자 ID 확인) 아는데, 누구에게 "신분증을 보여주세요!"(사용자 정보 가져오기)라고 말해야 할지 모르는 상황과 같습니다. 필요한 정보를 얻지 못합니다.
- 그냥 두면: 사용자 정보가 없어서 상세 페이지가 제대로 작동하지 않거나 오류가 발생할 수 있습니다.
- 선택지와 추천:
    *   (추천) 상세 페이지에도 대시보드와 동일하게 `getCurrentUser()`를 호출하여 사용자 정보를 가져오고, 그 정보로 영수증을 가져오거나 저장소를 생성하도록 지시합니다.
- 당신이 답할 질문: 상세 페이지에서 `getCurrentUser()` 함수를 호출하여 사용자 정보를 가져오도록 추가할까요?

### 9. 특정 코드 가져오기(`import`) 제한 규칙이 핵심 파일에 적용되지 않는다 [원문: S0 / C4]
- 무슨 문제: `CLAUDE.md`(=AI 설정 문서)에는 `C4`(=코드 의존성 규칙) 규칙에 따라 특정 라이브러리(`@anthropic-ai/sdk`, `@supabase/supabase-js`)를 `src/services/`나 `src/lib/supabase/` 폴더 밖에서 가져오지 말라고 되어 있습니다. 하지만 `handler.ts`(=요청 처리 파일)와 `deps.ts`(=의존성 모음 파일) 등 중요한 파일들이 이 `lint`(=코드 검사) 규칙 적용 대상에서 빠져 있습니다.
- 왜 중요한지 (비유): 중요한 물건은 특정 금고에만 보관하라고 규칙을 정했는데, 금고가 아닌 다른 서랍(핵심 파일)에 보관하는 것을 검사하지 않는 것과 같습니다. 규칙이 제대로 지켜지지 않습니다.
- 그냥 두면: 코드의 복잡성이 증가하고, 유지보수가 어려워지며, 예상치 못한 오류가 발생할 가능성이 높아집니다.

- 그냥 두면: 사용자가 숫자를 입력했지만 내부적으로 글자로 처리되어 오류가 발생하고, 데이터가 제대로 저장되지 않을 수 있습니다.

## 용어 사전
- `adaptive thinking`: AI가 스스로 생각하고 판단하는 방식. (예: 마치 사람이 주어진 정보를 바탕으로 고민하는 것과 비슷해요.)
- `anon`: 로그인하지 않은 사용자. (예: 웹사이트를 그냥 둘러보는 손님과 같아요.)
- `authenticated`: 로그인 한 사용자. (예: 회원가입하고 로그인해서 서비스를 이용하는 손님과 같아요.)
- `blocker`: 지금 막힘. (예: 핵심 부품이 고장 나서 공장 전체가 멈춘 것과 같아요.)
- `buildDeps`: 프로그램이 실행되기 위해 필요한 여러 부품(의존성)들을 만드는 과정. (예: 로봇을 만들기 위해 나사, 모터, 회로 같은 부품들을 조립하는 과정과 비슷해요.)
- `cache header`: 웹사이트의 데이터를 더 빠르게 보여주기 위해 "이 정보는 잠시 저장해두고 다시 쓰세요"라고 지시하는 정보. (예: 자주 보는 정보를 수첩에 적어뒀다가 다음에 바로 찾아보는 것과 같아요.)
- `catch()`: 만약 값이 없거나 문제가 생기면 "대신 이걸 넣어주세요"라고 알려주는 기능. (예: 요리하다 재료가 없으면 "대신 다른 재료로 대체해 주세요"라고 말하는 것과 같아요.)
- `C4`: 코드의 구조나 의존성을 정리하는 방법론 (여기서는 특정 모듈 사용 제한 규칙을 의미). (예: 레고 블록으로 집을 짓는데, 특정 블록은 반드시 특정 위치에만 써야 한다는 규칙과 같아요.)
- `CDN`: 웹사이트 데이터를 여러 곳에 분산 저장해서 사용자들이 더 빠르게 접근할 수 있게 해주는 기술. (예: 물류 창고가 전국 여러 곳에 있어서 어디서든 물건을 빠르게 받을 수 있는 것과 같아요.)
- `CLAUDE.md`: Claude AI 에이전트의 동작 방식이나 제약을 설명하는 문서. (예: AI 비서의 사용설명서 같은 거예요.)
- `CSS 변수 토큰`: 웹 디자인에서 색깔이나 크기 같은 반복되는 값을 미리 정해두고 이름으로 사용하는 것. (예: "메인 색깔은 파랑", "글자 크기는 16px"처럼 미리 정해놓고 필요한 곳에 "메인 색깔"이라고만 쓰는 거예요.)
- `DELETE`: 웹 서버에 데이터를 지워달라고 요청하는 명령. (예: "이 게시물을 삭제해 주세요"라고 게시판에 요청하는 것과 같아요.)
- `deps.ts`: 다른 파일들이 의존하는(사용하는) 도구들을 모아둔 파일. (예: 전기 회로를 만들 때 필요한 저항, 콘덴서 등 작은 부품들을 한 상자에 모아둔 것과 같아요.)
- `editor slot`: 화면에서 사용자가 내용을 입력하거나 수정할 수 있는 공간. (예: 게시판에서 글을 쓸 수 있는 빈 칸이나 수정 버튼을 누르면 나오는 편집 화면 같은 거예요.)
- `effort high`: AI가 문제를 해결하기 위해 최선을 다해 노력하라고 지시하는 것. (예: 비서에게 "모든 수단을 동원해서 최고로 완벽한 보고서를 만들어!"라고 지시하는 것과 같아요.)
- `exit 1`: 프로그램이 끝날 때 "내가 이렇게 끝났어요"라고 운영체제에 알려주는 숫자 신호. (예: 프로그램이 "작업 실패!"라고 말하고 종료하는 신호와 같아요.)
- `exit 2`: 프로그램이 끝날 때 "내가 이렇게 끝났어요"라고 운영체제에 알려주는 숫자 신호. (예: 'exit 1'과 비슷하지만, 여기서는 '실패했지만 특정 이유로 차단'을 의미해요.)
- `handler.ts`: 특정 요청을 처리하는 코드 파일. (예: 고객 센터에서 어떤 문의가 들어왔을 때, 해당 문의를 담당하는 직원이 처리하는 역할과 같아요.)
- `headless 세션`: 눈에 보이는 화면 없이 컴퓨터 안에서 조용히 진행되는 작업 과정. (예: 우리가 눈으로 보지 못하지만 컴퓨터 내부에서 자동으로 돌아가는 프로그램과 같아요.)
- `hero CTA`: 웹사이트 첫 화면에서 사용자의 클릭을 유도하는 가장 중요한 버튼. (예: "지금 바로 구매하기" 같은 메인 버튼이에요.)
- `input type="number"`: 숫자만 입력받도록 만든 입력칸. (예: 나이를 입력할 때 글자가 아닌 숫자만 입력되는 칸과 같아요.)
- `JSON 오류`: 오류 발생 시 컴퓨터가 이해하기 쉬운 형태로 만든 오류 메시지. (예: 컴퓨터가 "이러이러한 문제가 생겼어"라고 자기 언어로 설명해주는 오류 보고서와 같아요.)
- `JSON Schema`: 데이터가 어떤 형태여야 하는지 정해주는 설계도. (예: "고객 정보는 이름, 나이, 주소 순서로 적어야 해"처럼 데이터의 규칙을 정해주는 설계도와 같아요.)
- `lint`: 코드에 문법 오류나 스타일 실수가 없는지 검사하는 도구. (예: 맞춤법 검사기나 문법 검사기처럼 코드의 오류나 안 좋은 습관을 찾아주는 도구예요.)
- `major`: 곧 문제. (예: 지금은 괜찮지만 곧 엔진에 문제가 생겨 멈출 수도 있는 자동차와 같아요.)
- `마이그레이션`: 데이터베이스의 구조를 변경하는 작업. (예: 건물의 뼈대(데이터베이스 구조)를 바꾸기 위해 기둥이나 벽을 새로 만드는 공사와 같아요.)
- `max_tokens`: AI가 한 번에 답변할 수 있는 최대 글자 수. (예: AI 비서가 한 번에 말할 수 있는 최대 단어 수나 문장 길이를 제한하는 것과 같아요.)
- `maxDuration`: Vercel이라는 웹 호스팅 서비스에서 하나의 기능이 작동할 수 있는 최대 시간. (예: 특정 작업에 주어지는 최대 근무 시간 같은 거예요.)
- `mermaid`: 글로 그림을 그리는 도구. (여기서는 화면 흐름도를 의미). (예: 복잡한 순서도나 조직도를 글자로 쉽게 그릴 수 있게 해주는 프로그램이에요.)
- `minor`: 사소함. (예: 차에 작은 흠집이 난 것처럼 당장 문제는 없지만 거슬리는 정도예요.)
- `next-themes`: Next.js 앱에서 다크 모드를 쉽게 구현하게 해주는 도구. (예: 웹사이트의 테마(색상, 디자인)를 밝은 모드와 어두운 모드로 쉽게 전환해주는 플러그인 같은 거예요.)
- `Node`: 웹사이트나 앱을 만들 때 쓰는 컴퓨터 프로그램 실행 환경. (예: 게임을 컴퓨터에서 실행할 때 필요한 윈도우나 맥 같은 운영체제 환경과 비슷해요.)
- `no-restricted-imports`: "여기서는 특정 파일이나 도구를 가져오지 마세요"라고 규칙을 정하는 것. (예: 사무실에서 "이 부서에서는 저 부서의 서류를 직접 가져오지 마세요"라고 규칙을 정하는 것과 같아요.)
- `null`: "값이 없다"는 뜻. (예: 빈 상자나 아무것도 적히지 않은 칸과 같아요.)
- `package.json`: 프로젝트에 어떤 도구들이 필요한지 적어둔 목록 파일. (예: 요리할 때 필요한 재료 목록이나 레시피 카드와 같아요.)
- `PATCH`: 웹 서버에 데이터를 부분적으로 수정해달라고 요청하는 명령. (예: "게시물의 제목만 바꿔주세요"라고 요청하는 것과 같아요.)
- `pipeline`: 여러 작업이 순서대로 이어서 진행되는 과정. (예: 공장에서 여러 공정을 거쳐 제품이 만들어지는 과정과 같아요.)
- `PRD`: 제품 요구 사항 정의서. (예: 어떤 제품을 만들지, 어떤 기능이 필요한지 상세히 적어둔 청사진이에요.)
- `PreToolUse 훅`: AI가 어떤 도구를 사용하기 직전에 끼어들어 "잠깐, 이 도구 써도 돼?" 하고 점검하는 기능. (예: AI 비서가 특정 작업을 하기 전에 "이 작업, 해도 될까요?"라고 매니저에게 허락을 받는 것과 같아요.)
- `primary 액션`: 화면에서 가장 중요하고 눈에 띄는 행동 버튼. (예: 웹사이트에서 회원가입을 유도하는 "회원가입" 버튼처럼 가장 강조되는 버튼이에요.)
- `provider`: 구글 같은 외부 서비스. (예: 회원가입 시 구글이나 카카오톡으로 로그인하는 것처럼, 외부의 큰 서비스를 빌려 쓰는 개념이에요.)
- `proxy`: 웹사이트 요청을 대신 받아 처리해주는 중간 서버. (예: 직접 전화를 받기 어려울 때 비서가 대신 전화를 받아 처리해주는 것과 같아요.)
- `repository 예외`: 데이터베이스(저장소)와 관련된 작업에서 예상치 못한 문제가 발생한 상황. (예: 도서관에서 책을 찾거나 반납하는 중에 책이 훼손되거나 시스템 오류가 나는 것과 같아요.)
- `required`: "이 값은 반드시 있어야 해요"라고 지정하는 것. (예: 회원가입할 때 "이름은 반드시 입력하세요"라고 표시된 필수 입력 칸과 같아요.)
- `RLS 정책`: "데이터베이스의 이 줄은 누구만 볼 수 있어요"라고 접근 권한을 정하는 규칙. (예: 은행에서 "내 계좌 정보는 나만 볼 수 있다"고 정하는 규칙과 같아요.)
- `schema`: 데이터가 어떤 형태를 가져야 하는지 정의한 설계도. (예: '회원 정보는 이름, 이메일, 전화번호로 구성된다'와 같이 데이터의 형식을 미리 정해놓는 규칙.)
- `SDK`: 특정 서비스를 개발할 때 필요한 도구 모음. (예: 특정 브랜드의 가전제품을 고치기 위해 필요한 전용 연장 세트 같은 거예요.)
- `Set-Cookie`: 웹사이트가 사용자에게 보내는 작은 정보 조각으로, 사용자의 로그인 상태 등을 기억하는 데 쓰인다. (예: 웹사이트가 "이 사람은 로그인했어"라고 사용자 컴퓨터에 남기는 작은 메모와 같아요.)
- `setAll`: 여러 쿠키와 헤더를 한 번에 설정하는 함수. (예: 요리할 때 필요한 양념들을 한 번에 넣는 것과 같아요.)
- `Sonnet 5`: Anthropic이라는 회사에서 만든 AI 모델 이름. (예: 삼성 갤럭시나 애플 아이폰처럼, 특정 회사에서 만든 AI 모델의 고유한 이름이에요.)
- `stdin`: 컴퓨터에 정보를 입력하는 통로. (예: 키보드로 글자를 입력하는 것처럼 컴퓨터에게 명령이나 데이터를 넣어주는 통로예요.)
- `Stop 훅`: AI 작업이 끝날 때 "작업이 잘 끝났나 점검해줘"라고 호출되는 기능. (예: 공장이 제품 생산을 끝낸 후 품질 관리팀이 최종 검사를 하는 과정과 같아요.)
- `string type`: 데이터 종류 중 하나로, 글자(텍스트)를 의미. (예: 이름, 주소, 댓글 내용처럼 글자로 된 정보를 나타내는 형식이에요.)
- `subprocess.run`: 파이썬에서 다른 프로그램을 실행시키는 명령. (예: "터미널에서 이 명령어(다른 프로그램)를 실행시켜 줘"라고 파이썬에게 시키는 것과 같아요.)
- `table grant`: 데이터베이스의 특정 테이블(표)에 누가 어떤 작업을 할 수 있는지 권한을 주는 것. (예: 회사에서 특정 팀원에게만 특정 서류(테이블)를 보고, 수정하고, 지울 수 있는 권한을 주는 것과 같아요.)
- `Tailwind dark 커스텀 variant`: 웹 디자인 도구(Tailwind)에서 어두운 화면(다크 모드)에 특별한 스타일을 적용하는 방식. (예: 다크 모드일 때만 버튼 색깔을 진하게 바꾸는 디자인 규칙과 같아요.)
- `timeout`: 특정 작업을 기다리는 최대 시간. 이 시간을 넘으면 "기다리지 말고 중단해!"라고 명령하는 것. (예: 컵라면을 끓일 때 "3분만 기다려"라고 정해진 시간과 같아요.)
- `TimeoutExpired`: 어떤 작업을 기다리는 시간이 너무 길어져서 "더는 못 기다리겠어!" 하고 나타나는 오류. (예: 컵라면을 끓이는데 3분이 지나도 물이 안 끓어서 "더는 못 기다려!"라고 화내는 것과 같아요.)
- `Vitest`: 만든 프로그램이 잘 작동하는지 시험하는 도구. (예: 새로 만든 장난감이 설명서대로 잘 움직이는지 확인하는 시험 도구와 같아요.)
- `Zod`: 데이터가 올바른지 확인해주는 도구. (예: 입력된 정보가 '이름은 글자, 나이는 숫자여야 한다'는 규칙을 잘 지켰는지 검사해주는 도구와 같아요.)
- `@supabase/ssr`: Supabase라는 데이터베이스를 웹사이트에서 사용하기 쉽게 도와주는 도구. (예: 데이터베이스와 웹사이트를 연결해서 정보를 주고받기 편하게 해주는 중간 다리 역할의 도구예요.)
