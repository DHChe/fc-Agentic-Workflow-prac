## 1. 사람 (페르소나)

### 1.1 담당자 — 주 사용자
- 중소기업 경리·회계 담당 1인. 직원 15~30명분 지출 증빙을 혼자 모은다.
- 영수증은 직원이 카톡·메일로 사진을 보내거나, 종이로 책상에 두고 간다. 카드 명세서는 월초에 카드사 사이트에서 PDF로 받는다.
- 기기: 사무실 PC(크롬) + 개인 아이폰. **사진은 폰으로 받고, 정리·집계는 PC에서 한다.**
- 원하는 것: "이번 달 얼마 썼는지, 뭐에 썼는지"를 상사에게 빨리 보고. 엑셀에 손으로 옮기는 일을 없애고 싶다.
- 걱정: 숫자가 틀리면 본인 책임. 그래서 원본을 옆에 두고 확인하고 싶어 한다.
- 상황별 변형
  - **1.1a 첫날**: 초대 메일을 받고 처음 들어옴. 빈 화면. 뭘 해야 하는지 몰라야 정상.
  - **1.1b 평일**: 하루 0~5장을 수시로 폰에서 올림. 결과는 나중에 PC에서 봄.
  - **1.1c 월초**: 명세서 PDF를 올리고, 중복을 확인하고, 월간 보고서를 만들어 보냄.

### 1.2 관리자 — 프로젝트 소유자
- 앱 안의 역할이 아니다. Clerk 대시보드(담당자 초대, 시연 계정 생성)와 시드 스크립트를 다루는 사람이다. 앱에서는 담당자와 같은 화면을 본다.
- 관심사: 심사자가 언제 들어와도 동작하는가, 비용이 새지 않는가.

### 1.3 심사자 — 포트폴리오를 보는 사람
- 채용 담당자, 면접관, 동료 개발자. 포트폴리오 페이지의 링크로 와서 랜딩의 "시연 계정으로 들어가기" 버튼으로 입장한다. 입력할 로그인 정보는 없다.
- 머무는 시간 2~5분. 첫 화면 로딩이 10초면 나간다. 처리 대기는 다른 것을 둘러보며 1분까지는 견딘다.
- 기기: 대부분 PC 크롬. 가끔 폰.
- **올릴 영수증을 갖고 있지 않다** [G-1].
- 여러 명이 같은 날, 심지어 같은 시각에 같은 계정으로 들어올 수 있다.
- 무엇이든 눌러본다. 삭제 버튼도, 샘플 버튼 연타도.

## 3. 여정 (J)

### J1. 심사자의 5분 — 성공 기준 그 자체

포트폴리오 페이지에는 SlipScan 시연 주소만 적혀 있다. 시드 데이터는 고정 날짜(2026-08-01~2026-09-15)에 걸쳐 있고, 통계는 **거래가 있는 가장 최근 달**을 기본으로 연다 [G-3]. **전제: 재시드 직후**(표 아래 "샘플 재클릭").

| 순서(시각) | 심사자가 하는 것 | 화면에 보이는 것 | 느껴야 하는 것 | 어긋날 수 있는 지점 |
|---|---|---|---|---|
| 1 (0:00) | 링크 클릭 | 랜딩: 제목 한 줄, 특징 3개, 버튼 두 개("시연 계정으로 들어가기", "로그인"), 고지 두 줄(7.9) | 5초 안에 뭐 하는 앱인지 | 랜딩은 정적이라 DB 기상과 무관. Vercel 콜드스타트 1~2초 |

**샘플 재클릭**: 고정 샘플은 재시드 직후 첫 번째 클릭에서만 새 결제다. 두 번째부터는 같은 날짜·금액·끝4라 "중복(집계 제외)" 배지가 붙고 통계가 늘지 않는다. 그때는 7~8단계 대신 배지 + "원본 보기"가 시연이 된다. 자동 재시드·연타 방지는 넣지 않는다(PRD 10.3).

시연 계정에서 심사자가 **추가로 할 수 있는 것과 그 결과**
- 문서 삭제·업로드 누적 → 다음 심사자가 어질러진 화면을 봄 → 관리자가 시드 재실행 [G-2]
- 계정을 망가뜨리기 → 막혀 있다. 비밀번호는 아무도 모르므로 바꾸거나 오타로 잠글 수 없고, 계정 삭제는 Clerk 설정에서 꺼 두었으며, 시연 계정에는 사용자 메뉴 대신 "로그아웃"만 보인다 [G-4]
- 50회 소진 → 그날 다른 심사자는 열람만(H10)
- 자기 회사 영수증을 올림 → 다른 방문자에게 보임(랜딩 고지로 미리 알림)

### J2. 담당자의 첫날
1. 관리자가 Clerk 대시보드에서 보낸 초대 메일(한국어)을 받는다. 링크 클릭.
2. Clerk이 제공하는 가입 화면에서 이메일+비밀번호로 가입한다. 앱 안에 가입 화면은 없다.
3. 대시보드. 문서 0건, 통계는 "이 기간에는 거래가 없습니다", 보고서 없음. 업로드 구획이 맨 위에 있고 문서 목록 빈 상태에 "첫 영수증을 올려 보세요".
4. 책상 위 종이 영수증을 올리고 싶다. 폰으로 다시 로그인해 찍어 올리거나(J4), 폰 사진을 PC로 보내 올린다. 어느 쪽이든 앱은 관여하지 않는다.
5. 첫 결과를 본다. 카테고리가 마음에 안 들어도 못 고친다(PRD 10.1). 상세의 "금액 미인식"·"날짜 추정" 배지로 무엇을 못 읽었는지는 안다.
6. 헤더 사용자 메뉴에서 로그아웃.

### J3. 담당자의 월초 — 핵심 가치 여정
1. 카드사 사이트에서 지난달 명세서 PDF를 내려받는다. **대개 비밀번호(생년월일)가 걸려 있다.** 그대로 올리면 실패(사유: 암호 PDF) [G-7]. 카드사 뷰어에서 열어 암호 없이 다시 저장한 뒤 올려야 한다.
2. 업로드. 몇 분 동안 "처리 중".
3. 완료. 거래 30건. 그중 지난달에 올려 둔 영수증과 같은 결제 12건이 "중복(집계 제외)". 통계는 두 번 세지 않는다. 명세서의 취소 줄은 음수 금액으로 들어온다 [G-8].
4. 통계 ◀ → 지난달. 카테고리 비율 확인. 큰 카테고리의 내역은 문서 목록·상세에서 확인한다.
5. "이 달 보고서 만들기". 글 확인. 복사해서 상사에게 메일.
6. 다음 달에도 반복. 명세서를 실수로 두 번 올리면 두 번째 문서의 거래가 전부 중복 표시(UC-11 S4).

### J4. 담당자의 평일 — 모바일
1. 직원이 카톡으로 영수증 사진을 보낸다. 담당자 폰에 저장.
2. 폰 사파리에서 접속. 로그인이 유지돼 있으면 바로 대시보드.
3. 파일 선택 → 사진 보관함 → 올리기. 진행 막대. "처리 중". 아이폰이 사진을 HEIC 그대로 넘기면 7.2 형식 문구로 막힌다(감수, PRD 10.3).
4. 폰을 내려놓는다. 화면이 꺼지면 폴링이 멈추고, 다시 켜면 4초 안에 재개된다. 결과는 나중에 PC에서.
5. 3장 연속: 앞 건이 처리 중이어도 다음 건을 올릴 수 있다(PRD F3). 목록에 처리 중 3개.

### J5. 관리자의 준비 — 시연 전
1. Clerk 개발 인스턴스(공개에도 이 하나를 쓴다. ARCH ADR-29)를 Restricted로 두고 사용자 계정 삭제 기능을 끈다 [G-4].
2. Clerk 대시보드에서 시연 사용자를 직접 만든다(비밀번호는 무작위로 넣고 기록하지 않는다). 초대 절차는 필요 없다.
3. 그 사용자의 userId → `DEMO_USER_ID` → 시드 실행. 문서 10건 + 2026년 8월 월간 보고서 1건. 날짜는 2026-08-01~2026-09-15 고정. `DEMO_USER_ID`가 비어 있으면 시드는 즉시 중단한다.
4. 포트폴리오에 주소만 게시한다.
5. 공개 후: 주 1회 Claude usage 로그와 Blob 사용량 확인(ARCH 11). 시연 계정이 어질러졌으면 시드 재실행(멱등) [G-2].
6. 담당자를 들일 때는 Clerk 대시보드에서 초대를 보낸다.

### J6. 몇 주 만의 복귀 — 담당자·심사자 공통
1. 접속. Vercel 함수 콜드스타트 1~2초 + Neon 기상 1초 미만. 랜딩은 정적이라 즉시.
2. Clerk 세션이 살아 있으면 `/`에서 대시보드로 자동 이동. 만료면 담당자는 로그인, 심사자는 버튼을 다시 누른다.
3. 그동안 "처리 중"으로 남아 있던 문서는 조회 시 실패로 바뀌어 보인다(ARCH 5.2). 통계는 거래가 있는 가장 최근 달을 연다 [G-3].

## 5. 유스케이스 (UC)

형식: 행위자 / 사전조건 / 기본 흐름 / 대안(A)·예외(E)·변형(V)·시나리오(S) / 사후조건 / 출처. UC-02, 14, 18은 결번(2026-09-17 컷).

### UC-01 랜딩 방문

### UC-03 로그인·로그아웃·세션
- 기본: `/sign-in`에서 이메일+비밀번호 → 대시보드(또는 `redirect_url`). 초대받아 가입한 사용자용이다.

- A2 로그아웃: 헤더 오른쪽 사용자 메뉴(Clerk `UserButton`) → 랜딩. 시연 계정은 메뉴 대신 "로그아웃" 버튼만 [G-4].
- A3 시연 로그인: 랜딩의 "시연 계정으로 들어가기" → 서버가 일회용 sign-in token을 만들어 로그인시킨다 → 대시보드. 입력 없음 [G-4]. 흐름은 ARCH 5.7.
- E1 API 호출이 401 → 로그인 화면으로. 진행 중이던 업로드는 사라짐(다시 올린다). **폴링 중 401이면 폴링을 멈추고** 로그인 화면으로 간다.

- 출처: F2, F11

### UC-04 대시보드 진입
- 기본(데이터 있음): 구획 순서 업로드 → 통계(기본 달 [G-3]) → 문서 목록 → 보고서 목록. 헤더에 "오늘 사용 n/50".
- 데이터 읽기 규칙: 첫 로드, 4초 폴링, 업로드·보고서 직후에 `GET /api/dashboard` **하나**로 문서 목록·통계·사용량을 함께 읽는다. 장치는 이 하나다. 보고서 목록은 첫 로드와 보고서 생성 직후에만 읽는다.
- V1 빈 상태(첫날): 7.1의 빈 상태 문구 3개. 업로드 구획이 맨 위.
- V2 처리 중 문서 있음: 4초 폴링 시작(직전 요청이 끝나지 않았으면 건너뜀). 완료되면 목록과 통계가 같은 주기에 바뀐다.
- 출처: PRD 5절, ARCH 5.2

### UC-05 영수증 사진 업로드 (PC)
- 사전: 로그인, 오늘 사용 < 50.
- 기본
  1. 파일 선택(클릭) → 파일명·크기 표시.
  2. "올리기" → 브라우저 검사(형식·크기) → 토큰 요청(**이 시점에 사용 +1**) → Blob 직접 업로드(진행률 표시, C4) → `POST /api/documents` → 목록 맨 위에 "처리 중" 행, 폼 초기화. 저장 경로와 검증 규칙은 ARCH 5.1.
- A1 앞 문서가 처리 중 → 그대로 다음 파일을 올린다(허용).
- A2 "샘플로 해보기" [G-1] → 브라우저가 `public/samples/`의 가짜 영수증을 받아 같은 경로로 올린다. 사용 +1.
- E1 지원하지 않는 형식(WebP·GIF·HEIC·DOCX 등) → 선택 즉시 7.2 형식 문구. 올리기 비활성.
- E2 10MB 초과 → 7.2 크기 문구. 올리기 비활성.
- E3 업로드 실패 공통 규칙(토큰 거절, Blob 업로드 끊김, `POST /api/documents` 실패 모두): 브라우저가 대시보드를 다시 읽는다. 사용량이 50이면 7.3의 429 문구 + 버튼 비활성, 아니면 7.2 업로드 실패 문구.
- E4 Blob 업로드 중 네트워크 끊김 → E3. 토큰 발급 뒤라면 이미 1회 차감된 상태다.
- E5 Blob 성공 후 `POST /api/documents` 실패 → E3. 고아 파일 1개(ARCH 5.1 감수). 재시도하면 새 uploadId로 새 문서가 되고 1회가 더 든다.
- E6 파일을 골라 둔 사이에 한도 도달(다른 탭, 다른 심사자) → 토큰 거절 → E3.
- 사후: `documents` 1행(processing). 오늘 사용 +1(토큰 발급 시점).
- 출처: F3, PRD 7절, ARCH 5.1

### UC-06 카드명세서 PDF 업로드
- UC-05의 기본 흐름과 같다. 다른 점만 적는다.
- 처리 시간 몇 분. 폴링이 계속된다.
- A1 명세서를 사진으로 찍어 올림 → 이미지지만 문서 종류는 명세서, 거래 여러 건. 정상.
- A2 영수증 여러 장을 한 PDF로 스캔, 또는 책상에 펼쳐 놓고 한 장의 사진으로 찍음 → 문서 종류가 영수증이어도 거래 N건(확인 항목 C2).
- E1 20페이지 초과 → 업로드는 성공, 잠시 뒤 실패(7.4 페이지 초과).
- E2 암호가 걸린 PDF → 실패(7.4 암호 PDF) [G-7]. 한국 카드사 명세서의 기본 상태라 흔하다.
- E3 명세서에 취소·환불 줄 → 음수 금액 [G-8].
- E4 거래가 수백 건인 명세서 → 실패할 수 있다(7.4 해석 실패). 감수(PRD 10.3).
- 출처: F3, F4

### UC-07 모바일 업로드
- 기본: 폰 브라우저 → 파일 선택 → OS 선택지(사진 보관함 / 카메라 / 파일). `capture` 속성은 쓰지 않는다. 이유: 카메라를 강제하면 보관함 사진을 고를 수 없다.
- 큰 사진·눕은 사진: 서버가 분석용 사본에서 회전·축소한다(ARCH 5.1). 저장 원본은 그대로이고, 미리보기는 브라우저가 EXIF 회전대로 보여준다. 사용자는 이 과정을 모른다.
- E1 폰 사진이 10MB 초과(드묾) → UC-05 E2. "사진 크기를 줄여 주세요"까지는 안내하지 않는다.
- E2 업로드 중 화면이 꺼짐 → 업로드 끊김 → UC-05 E4.
- E3 아이폰이 사진을 HEIC 그대로 넘김 → UC-05 E1(감수).
- 출처: F3

### UC-08 처리 중 기다리기
- 기본: 목록에 "처리 중" 배지 + 업로드 시각. 문서 종류·건수·합계 칸은 "—". 4초 폴링. 완료되면 채워지고 통계도 같은 주기에 갱신(UC-04).
- A1 화면을 떠남 → 돌아오면 최신 상태.
- A2 탭을 닫음 → 후처리는 서버에서 계속된다(`after`).
- A3 여러 건 동시 처리 중 → 각각 독립.
- A4 처리 중 문서의 상세를 열면 → 원본은 보이고 거래 표 자리에 7.1 "분석 중입니다" 문구.
- A5 폰 화면이 꺼짐 → 폴링이 멈췄다가 화면을 켜면 4초 안에 재개. 별도 처리 없음.
- E1 10분 경과 → 다음 조회 때 실패(7.4 처리 시간 초과).
- E2 처리 중 삭제 시도 → 삭제 버튼 비활성 + 7.6 문구 [G-9].
- E3 폴링 응답이 401 → 폴링 중단, 로그인 화면(UC-03 E1).
- 출처: F5, ARCH 5.2

### UC-09 추출 결과 확인 (문서 상세)
- 기본: 원본(이미지는 인라인, PDF는 "원본 열기" 새 탭 링크) + 거래 표. 열: 거래일시, 가맹점, 금액, 카테고리, 카드 끝4, 배지. 머리에 문서 종류·업로드 시각·사용 모델·문서 합계.
- 문서 합계 = 추출된 금액의 합(미인식 제외, **중복 포함**) [G-10]. 통계와 기준이 다르며, 중복은 배지로만 알린다.
- V1 영수증 1건: 표 1행.
- V2 명세서 N건: 표 N행. 취소 줄은 음수로 표시("-23,000원") [G-8].
- V3 거래 0건(문서 종류가 `기타`이거나, 영수증·명세서로 판별됐지만 읽은 거래가 없음): 7.1 "추출할 거래가 없습니다" 문구. 원본은 보인다. 세금계산서·거래명세서·이체확인증은 `기타`로 떨어진다.
- V4 금액 미인식: 금액 칸 "—" + "금액 미인식" 배지. 통계 제외. 0원은 미인식이 아니라 정상 거래다.
- V5 날짜 추정: 날짜 옆 "날짜 추정" 배지(업로드일로 대체됨). 미래 날짜로 읽힌 경우도 프롬프트 규칙(C2)에 따라 여기로 온다.
- V6 중복: "중복(집계 제외)" 배지 + "원본 보기" 링크 → 원본 거래가 있는 문서 상세.
- V7 카테고리 오판: 알아채도 못 고친다(PRD 10.1). "삭제 후 재업로드"를 권하는 문구는 넣지 않는다. 이유: 같은 결과가 나올 확률이 높다.
- V8 부분 인식(가맹점 null, 금액 있음): 가맹점 "—". 통계 포함.
- 출처: F4, F5, PRD 8절

### UC-10 실패 문서 처리
- 기본: 목록·상세에 "실패" 배지 + 사유 한 줄(7.4의 문장 그대로, DB 값과 같음). 재시도 버튼 없음. 삭제 → 다시 올린다.
- 사용 횟수는 이미 차감돼 있다. 재업로드는 +1.
- 출처: F5, ARCH 8

### UC-11 중복 감지
- S1 영수증(9/3, 23,000원, 카드 1234) 먼저 → 명세서 나중: 명세서의 그 한 줄이 중복.
- S2 명세서 먼저 → 영수증 나중: 영수증 거래가 중복. 영수증 문서의 합계는 23,000원으로 보이되(중복 포함 [G-10]) 배지가 "집계 제외"를 알린다.
- S3 같은 영수증을 두 번 올림: 두 번째가 중복("샘플로 해보기" 재클릭이 이 경우다).
- S4 명세서를 두 번 올림: 두 번째 문서의 거래 전부가 중복.
- S5 같은 날 같은 금액을 실제로 두 번 결제(커피 2번), 영수증 2장, 카드 끝4 같음 → 두 번째가 중복으로 **오판**. 풀 수단 없음(PRD F7). 명세서에 두 줄로 나오면 그 둘은 서로 비교하지 않는다(같은 문서).
- S6 카드 끝4가 없는 현금영수증 → 날짜+금액+가맹점명으로 비교. 가맹점명 표기가 다르면("스타벅스" vs "스타벅스코리아") 못 잡는다(감수, 8.4). 끝4와 가맹점명이 둘 다 없으면 비교하지 않는다.
- S7 원본 문서를 삭제 → 그 원본을 가리키던 거래가 전부 정상으로 돌아오고 통계에 다시 포함(UC-12 V1). 되돌아온 거래끼리의 재중복은 다시 판정하지 않는다(감수).
- S8은 결번(직원명 컷).
- S9 할부 결제: 명세서엔 월 분할액, 영수증엔 전액 → 금액이 달라 중복을 못 잡는다(감수, 8.4).
- 날짜 추정 거래는 비교 대상·후보 모두에서 빠진다. 업로드일이 우연히 같을 수 있어서다.
- "나중"의 기준은 거래일이 아니라 **들어온 순서**(`created_at`)다.
- 출처: F7, ARCH 5.5

### UC-12 문서 삭제
- 기본: 상세(또는 목록 행)에서 삭제 → 확인 대화(7.6) → 삭제 → 목록으로.
- V1 중복의 "원본"이던 문서 → 그것을 가리키던 거래가 전부 정상으로 돌아온다. 통계 숫자가 바뀐다.
- V2 보고서에 쓰인 거래 → 보고서는 그대로(F5).
- V3 처리 중 → 버튼 비활성 [G-9].
- V4 실패 문서 → 삭제 가능(파일도 삭제).
- V5 다른 탭에서 이미 삭제됨 → 404 → 7.3 문구.
- 삭제해도 오늘 사용 횟수는 줄지 않는다(UC-17).
- 출처: F5, ARCH 5.6

### UC-13 기간 통계
- 기본: 월 단위. ◀ ▶ + 현재 달 라벨("2026년 9월"). 날짜 선택기 없음. 총액, 건수, 카테고리별 금액·비율. 총액이 0 이하이면 비율 칸은 "—".
- 기본 달 [G-3]: **거래가 있는 가장 최근 달**(오늘 이후 날짜의 거래는 빼고 찾는다). 거래가 하나도 없으면 이번 달.
- V1 해당 달 거래 0건 → 7.1 문구. 보고서 버튼 비활성.
- V2 처리 중 문서가 완료 → 같은 폴링 주기에 숫자 갱신(UC-04).
- V3 날짜 추정 거래 → 업로드일 기준으로 들어간다. 통계 화면에 별도 표시 없음(상세에서만).
- V4 음수 거래 → 그대로 합산(순지출) [G-8].
- V5 달 경계는 한국 시간이다.
- 출처: F7, ARCH 5.4

### UC-15 보고서 생성
- 사전: 로그인, 사용 < 50, 그 달에 집계 대상 거래 ≥ 1건.
- 기본: 통계 구획의 "이 달 보고서 만들기" [G-5] → 같은 화면의 보고서 영역에 글이 흐른다 → 스트림이 끝나면 화면이 그 보고서의 상태를 조회해 판정한다. 완료면 7.5 완료 문구, 보고서 목록 맨 위 + "열기". 아니면 7.5 중단 문구.
- V1 같은 달을 또 만듦 → 둘 다 보관, 생성 시각으로 구분.
- V2 아직 끝나지 않은 달(오늘이 9/17인데 9월 보고서) → 만들 수 있다. 별도 표시 없음.
- E1 스트리밍 중 새로고침·탭 닫기 → 브라우저 이탈 경고(7.5). 나가면 저장을 보장하지 않는다(서버가 끝까지 받으면 남을 수 있다). 사용 +1은 유지.
- E2 스트리밍 중 앱 안에서 다른 화면으로 이동 → E1과 같다. 보고서 목록은 완료된 것만 보이고, 미완성 서버 행은 10분 뒤 조회 때 `abandoned`(ARCH 5.3).
- E3 429 → 버튼 비활성 + 7.3 문구.
- E4 글이 한 글자도 오기 전에 실패 → HTTP 오류 문구(7.3. Claude 장애는 502). 사용 +1(실패 포함).
- E5 글이 오던 중 끊김 → 부분 글은 화면에 남고 7.5 중단 문구.
- E6 폰에서 화면이 꺼져 스트림이 끊김 → E5.
- 출처: F8, ARCH 5.3

### UC-16 보고서 열람
- 기본: 목록(달, 생성 시각. **완료된 것만**) → 상세(마크다운 렌더, 5개 섹션, "복사" 버튼).
- 본문의 링크·이미지는 표시하지 않는다. 생성 중 화면도 같은 규칙이다(ARCH 7.3).
- 보고서 삭제는 없다(PRD에 없음).
- 출처: F8

### UC-17 사용량 한도
- 기본: 헤더에 "오늘 사용 n/50". UC-04의 데이터 읽기 규칙으로 갱신된다(별도 규칙 없음). 문서·보고서를 지워도 줄지 않는다(ARCH 6절).
- 50 도달: 업로드·보고서 버튼 비활성 + 7.3의 429 문구.
- V1 자정이 지남(화면 그대로) → 다음 폴링이나 새로고침 때 바뀐다.
- V2 시연 계정을 여러 심사자가 써서 소진 → 다음 심사자는 처음부터 비활성 상태를 본다.
- 출처: F9, ADR-13

### UC-19 시연 계정 운영
- 입장: 랜딩의 "시연 계정으로 들어가기"(UC-03 A3). 비밀번호는 아무도 모른다 [G-4].
- 여러 심사자 동시: 서로의 업로드가 같은 목록에 섞여 보인다. 원본은 공개 주소(ADR-14)라 다른 방문자가 열 수 있다 → 랜딩 고지 두 번째 줄(7.9)로 미리 알린다.
- 어지르기와 복구: 삭제·업로드 누적 → 관리자가 시드 재실행 [G-2]. 계정 삭제는 Clerk 설정으로 막고, 사용자 메뉴 대신 로그아웃만 보인다 [G-4].
- 샘플 재클릭: 재시드 뒤 두 번째부터 중복 판정(J1 "샘플 재클릭").
- 시드 날짜는 고정(2026-08-01~2026-09-15). 통계 기본 달이 "거래가 있는 최근 달"이므로 시간이 지나도 첫 화면이 비지 않는다 [G-3].
- 출처: F11, ARCH 11

### UC-20 모바일 열람
- 목록·상세·통계·보고서를 폰 너비에서. PDF는 "원본 열기"로 새 탭(PC와 같은 규칙).
- 스트리밍 보고서는 폰에서도 동작한다. 화면이 꺼지면 UC-15 E6.
- 출처: PRD 9(비기능), J4

### UC-21 테마
- 라이트만. 기기의 다크 설정을 따르지 않는다. 배지 6종(처리 중/완료/실패/금액 미인식/날짜 추정/중복)은 design.md 6.2의 색과 글자로 구분한다(금액 미인식·날짜 추정은 같은 색).
- 출처: PRD 9, ADR-16

### UC-22 오류 화면 공통
- 404(없는 문서·보고서, 남의 것), 500: 7.3 문구 + 대시보드 링크.
- 출처: ARCH 8

## 6. 상태 (사용자 눈으로)

### 6.1 문서
```
업로드 성공 ──▶ 처리 중 ──▶ 완료 (거래 0건 이상)
                 │
                 ├──▶ 실패 (사유 한 줄)
                 └──(10분 경과, 조회 시 판정)──▶ 실패 (처리 시간 초과)

삭제: 완료·실패에서만. 처리 중에는 버튼 비활성 [G-9]
```

### 6.2 거래 배지 (겹칠 수 있음)
| 배지 | 조건 | 통계 | 보고서 |
|---|---|---|---|
| (없음) | 정상 | 포함 | 포함 |
| 금액 미인식 | 합계금액 없음(0원은 해당 없음) | 제외 | 제외 |
| 날짜 추정 | 거래일 못 읽음(미래 날짜 포함) → 업로드일 | 포함(업로드일 기준) | 포함 |
| 중복(집계 제외) | 중복 감지됨 | 제외 | 제외 |

음수 금액(취소·환불)은 배지 없이 금액 칸에 음수로 보인다 [G-8]. 날짜 추정 거래는 중복 비교에서 빠진다.

### 6.3 보고서
```
버튼 ──▶ 생성 중 (화면에 글이 흐름) ──▶ 완료 (저장, 목록에 표시)
             └──▶ 중단 (이탈·오류. 목록에 보이지 않음)
```
완료 판정: 스트림이 끝난 뒤 화면이 보고서 상태를 조회해 `completed`면 완료, 아니면 중단이다(ARCH 5.3).

## 7. 문구 목록 (고정 한국어, 단일 출처)

ARCH 8절 규약대로 서버가 주는 문장을 화면이 그대로 쓴다. 구현 때 이 절 전체를 상수 파일 하나(`lib/messages.ts`)로 옮긴다. 본문의 다른 곳에서 인용한 문장은 모두 여기 있는 것과 같아야 한다.

| 문서 상세(처리 중) | 분석 중입니다. 잠시 후 다시 확인해 주세요. |

### 7.3 API 오류 (`{ error }`)
| 코드 | 문구 |
|---|---|
| 400 | 요청이 올바르지 않습니다. |
| 401 | 로그인이 필요합니다. |
| 404 | 문서를 찾을 수 없습니다. / 보고서를 찾을 수 없습니다. |
| 429 | 오늘 한도(50회)를 모두 사용했습니다. 한국 시간 자정에 초기화됩니다. |

### 7.4 문서 실패 사유 (`failure_reason`에 저장되는 값 그대로)
| 원인 | 문구 |
|---|---|

| 암호 PDF(명시적 암호 오류만) [G-7] | 암호가 걸린 PDF는 처리할 수 없습니다. 암호를 풀어 저장한 뒤 올려 주세요. |
| 10분 초과 | 처리 시간을 초과했습니다. |
| DB·그 외 | 알 수 없는 오류가 발생했습니다. |
